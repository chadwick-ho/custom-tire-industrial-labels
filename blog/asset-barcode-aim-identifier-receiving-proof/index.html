Industrial Barcode Labels: Check Whether the Reader Sends an AIM Symbology ID

Published November 14, 2026

An asset receiving application expects to distinguish a GS1 DataMatrix symbol from another Data Matrix workflow. A reader shows a short identifier before the decoded fields. The label buyer needs to know whether that identifier is scanner metadata and which receiving configuration relies on it.

Record the receiving interface before changing the code

Ask the owner to record the approved carrier and data syntax, then capture what the installed reader sends over its actual interface. Keep any AIM identifier apart from the payload in the evidence. A visible prefix can be sent by the reader rather than printed as characters inside the barcode. Check the exact scanner profile and compare the captured input with what the application parses and stores.

If the receiver routes by carrier metadata, ask it to test one accepted symbol and a controlled alternate. Check which parser handles each, what the application retains and what it rejects. If the receiver does not use this metadata, leave the barcode artwork unchanged while the owner reviews how the reader presents its output.

Zebra’s DataWedge barcode input documentation describes its AIM Code ID option and distinguishes it from a vendor-defined code ID. The receiver should confirm the behavior of its own hardware and interface.

Approved symbolCarrier, intended syntax and authorized sample data.
Raw captureReader model, interface and transmitted metadata separate from the decoded field.

Change ownerReceiver owner decides how metadata is expected before print approval.

Before approving the order

Hold if the system cannot distinguish a required carrier or stores the identifier as part of the wrong field. A configurable site prefix with no symbology meaning needs the site’s ordinary prefix review.
